What is ssh?

SSH (Secure Shell) is a cryptographic network protocol for secure remote login, command execution, and file transfer between hosts. It authenticates users, encrypts traffic, supports port forwarding and tunneling, and replaces insecure protocols like Telnet and rsh for system administration and automation.

ssh tunneling

ssh -N -L 0.0.0.0:PORT:127.0.0.1:PORT USERNAME@IP
  • ssh
    • The SSH client program used to create a secure, encrypted connection to a remote host.
  • -N
    • Tells SSH not to execute a remote command or open a remote shell.
    • Used when you only want to do port forwarding or tunneling, without an interactive session.
  • -L 0.0.0.0:PORT:127.0.0.1:PORT
    • Enables local port forwarding.
    • General format: -L [bind_address]:local_port:target_host:target_port
    • 0.0.0.0 (bind address)
      • Bind the local listening socket on all network interfaces of the client machine.
      • This means other hosts that can reach your machine can also use this forwarded port (if firewall allows).
    • PORT (first one)
      • The local port on your machine that will listen for incoming connections.
      • Example: if you use 8080, other apps can connect to your_ip:8080.
    • 127.0.0.1 (target host)
      • The host as seen from the remote SSH server.
      • Here, it means “the remote server itself” (its own loopback interface).
    • PORT (second one)
      • The target port on the remote side that traffic will be forwarded to.
      • Often the same as the local port, but it doesn't have to be.

    ssh establishment

    Case 1 : ssh-keygen

    steps

    • 1. Generate keypair
      ssh-keygen -t ed25519 -C "you@example.com"
      Accept default path (~/.ssh/id_ed25519) and set a passphrase (recommended).
    • 2. Copy <generated.pub> and paste on /.ssh/authenticated_keys on the target machine.
      cat /home/<username>/.ssh/id_ed25519.pub
      copy output and paste it on the target machine... echo <output> > /home/<target_user>/.ssh/authenticated_keys
    • 3. Access with
      ssh -i ~/home/username/.ssh/<your_private_key> usermane@target_ip

    Case 2 : id_rsa

    steps

    • 1. On the target machine, find /.ssh dir.
    • 2. In the .ssh dir, find id_rsa file.
      cat /home/target_user/.ssh/id_rsa
    • 3. Copy and paste it on your local machine
      echo 'output' > id_rsa
    • 4. Authorize the file.
      chmod 600 id_rsa
    • 5. Use it for conneciton
      ssh -i id_rsa username@target_ip

    3. When you cannot establish connection

    Why -o PubkeyAcceptedKeyTypes=ssh-rsa works on old boxes

    • Root cause: Modern OpenSSH clients disable RSA/SHA-1 signatures (the legacy algorithm named ssh-rsa) by default. Many old servers only support ssh-rsa and don’t support the newer RSA-SHA2 signatures.
    • Symptom: ssh -i hype_key_decrypted hype@<target_ip> fails public-key auth even though the key is correct.
    • Fix: Explicitly allow the legacy algorithm so your client will offer it.

    Commands

    kali@kali:~ $ ssh -o PubkeyAcceptedAlgorithms=+ssh-rsa -o HostkeyAlgorithms=+ssh-rsa \
  -i hype_key_decrypted hype@<target_ip>

# On older clients (option name alias):
kali@kali:~ $ ssh -o PubkeyAcceptedKeyTypes=+ssh-rsa -i hype_key_decrypted hype@<target_ip>
    • PubkeyAcceptedAlgorithms (or older PubkeyAcceptedKeyTypes) lets your client sign with ssh-rsa for user auth.
    • HostkeyAlgorithms may also be needed if the server’s host key itself is only ssh-rsa.
    • Tip: Use the + prefix to append (not replace) the defaults.

    Quick checks

    kali@kali:~ $ ssh -vvv -i hype_key_decrypted hype@<target_ip>   # see which algos are offered/refused
    • Permissions: chmod 600 hype_key_decrypted, and ensure the remote ~/.ssh/authorized_keys has the matching public key.
    • Typo watch: Use hype@<target_ip> (a double @ will fail).
    • Security note: ssh-rsa (RSA/SHA-1) is legacy—enable it only when necessary for old targets.

    Real Case

    Force a specific MAC (integrity algorithm) with a key

    kali@kali:~ $ ssh -o MACs=hmac-sha2-256 -i id_rsa djmardov@10.129.69.182
    • ssh: open an SSH session to a remote host.
    • -o MACs=hmac-sha2-256: tell the SSH client to use the listed Message Authentication Code algorithm(s) for integrity (not encryption). Here we force hmac-sha2-256, which many servers prefer over legacy HMACs.
    • -i id_rsa: use this private key for authentication (ensure chmod 600 id_rsa).
    • djmardov@10.129.69.182: username and target host.

    When to use

    • Server only allows certain MACs, or your policy forbids weak ones.
    • Handshake fails with messages about “no matching MAC found”.

    Tips

    # See MACs your client supports
kali@kali:~ $ ssh -Q mac

# Offer multiple MACs in order (client picks the first mutually supported)
kali@kali:~ $ ssh -o MACs=hmac-sha2-512,hmac-sha2-256 -i id_rsa user@host

# Persist for a host in ~/.ssh/config
Host lab-irked
  HostName 10.129.69.182
  User djmardov
  IdentityFile ~/.ssh/id_rsa
  MACs hmac-sha2-256
